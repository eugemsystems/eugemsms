# Intelligence

## Report builder: every filter, group-by and selected field is checked against the runner, server-side
ExecuteCustomReportAction must validate each filter and group-by field (registered, filterable/groupable, readable by the RUNNING user) as well as each selected field — a predicate over an unreadable field (e.g. WHERE basic_salary_minor > N) is an inference oracle even if the column is never selected. Column aliases are concatenated into SQL, so they must match /^[A-Za-z_][A-Za-z0-9_]{0,63}$/. RunSavedReportAction only runs for the author or a share recipient (user or role). Field permission checks go through ReportFieldAccess, which treats a never-created permission as "not permitted" (spatie throws PermissionDoesNotExist otherwise). Livewire properties are client-tamperable: UI pickers are a convenience, the Action is the defence.

## Early-warning data is staff-only; wellbeing is own + line manager, no override
INT-03 risk scores/factors/flags are never exposed to learner or guardian surfaces and nothing contacts a guardian (BR-INT-03-002/004). Staff wellbeing goes through StaffWellbeingVisibility (own record + reports_to_staff_id reports) for every read AND write — no school-wide override, re-derived per call. Weights only for registered learner indicators, bounded 0-100 (SetRiskScoreWeightAction). Flag closure needs an intervention note and a closed flag cannot be re-reviewed. Screens live under Livewire/EarlyWarning/.

## Report export (PDF/Excel/CSV) and `/api/v1/reports/*` are built — the only new Composer dependencies this codebase has added mid-stream (2026-10-08, user-approved)
`barryvdh/laravel-dompdf` + `maatwebsite/excel` were added specifically for this gap, with the user's explicit approval (CLAUDE.md requires it for any new dependency) — don't assume either is available in an older checkout, and don't add a third export engine without the same approval. `GenerateReportExportAction` renders an already-run `ReportResult` to csv/excel (via `Excel::raw()` + the generic `ReportResultExport` FromArray/WithHeadings class) or pdf (via `Pdf::loadHTML()->output()`) — it never re-runs or re-authorises the report itself. `Reports\Index`'s own `export()` method and `/api/v1/reports/{ulid}/export?format=` both call it after their own `RunSavedReportAction` call. The API surface (`entities`/`run`/`export`) authenticates via `serp.api-client:reports:read` (a NEW ability, the first one actually enforced through the `serp.api-client:{ability}` middleware-param mechanism — `usage:read` is issuable but has no route checking it yet) and acts as the API key's own `created_by` user: a key can only run/export what the person who issued it could themselves see, via the exact same `RunSavedReportAction`/`GetAvailableFieldsForUserAction` re-evaluation every human viewer gets (BR-INT-01-005) — no separate API-only privilege path was invented.

## Custom reports: edit/delete, schedule pause/delete, and cron wiring are built (2026-10-08)
`UpdateCustomReportAction` only renames/re-describes/re-charts a saved report — the query itself (entity, fields, filters) is never re-opened; a different query is a new report via `Reports\Builder`. `DeleteCustomReportAction` is a real hard delete; `custom_report_schedules`/`report_shares` cascade-delete on `report_id` already, so nothing orphans. `SetCustomReportScheduleActiveAction` (pause/resume) mirrors `SetWebhookSubscriptionActiveAction`'s own shape. The `intelligence.run_scheduled_reports` cron task (hourly, per-school) now actually calls `RunScheduledReportsAction` for every due `CustomReportSchedule` — this was previously registered-but-never-wired; `Reports\Schedule`'s own docblock used to say so. All of `Index`/`Schedule`'s own-report/own-schedule ownership checks follow the existing `ownReport()` pattern: the Action trusts the caller already validated ownership, same as `ShareReportAction`.

## Vendor usage aggregate is built; webhook domain-event wiring and the attendance hardware route are deliberately not (2026-10-08)
`Saas\Vendor\Usage\Index` (BR-INT-04-011) gives the vendor console a cross-tenant total + per-tenant breakdown over `api_usage_log`, `withoutGlobalScope(SchoolScope::class)` like `Vendor\Adoption` already does. `TriggerWebhooksForEventAction`/`HardwareScanRouteRegistry`'s own docblocks flag webhook-to-domain-event auto-firing and an `attendance` hardware route as open — both are left alone on purpose: wiring webhooks to the app's ~100+ domain events has no established wildcard-listener pattern anywhere in this codebase (every module wires one `Event::listen(Specific::class, Specific::class)` at a time) and would be a new cross-cutting pattern, not a bounded fix; the attendance route needs a timetable-aware "which session is live" resolver this pass does not build, and a guessed one would be worse than the documented gap (the registry's own words). Don't build either without checking in first.

## Webhook targets: public https only, re-checked at every dispatch
Webhook URLs are server-side-fetched, so WebhookTargetUrl::assertSafe() runs on create AND on every DispatchWebhookAction attempt (https only, no credentials, no localhost/private/link-local/reserved IPs, DNS-resolved addresses checked, redirects never followed). A subscription's client must be an active integration client of the same school. API keys, signing secrets and SSO credentials are shown once / write-only — never reloaded into a screen. The Clients screen only touches client_type=integration; device credentials belong to the Hardware screen.
