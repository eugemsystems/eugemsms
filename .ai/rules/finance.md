# Finance

## A 'date'-cast column stores full datetime — never compare against a bare toDateString() cutoff
A model attribute cast as `'date'` (e.g. `journal_lines.effective_at`) still serialises to a full datetime string on write in this Laravel version (e.g. "2026-09-09 00:00:00", not "2026-09-09"). A `WHERE column <= '2026-09-09'` comparison against that stored value is a **lexicographic string comparison** in both MySQL and SQLite: "2026-09-09 00:00:00" sorts *after* "2026-09-09" (same prefix, more characters), so the row is silently excluded even though the date is exactly equal — an "as at today" balance/trial-balance query returns zero for everything posted today.

**Why:** `CalculateAccountBalanceAction`, `CalculateSubledgerBalanceAction`, and `GenerateTrialBalanceAction` all originally compared `effective_at <= $asAt->toDateString()` and silently returned 0 for every account with same-day activity — caught by a balance assertion in a test, not by any error.

**How to apply:** any "as at [date]" cutoff comparison against a `date`-cast column must use `$asAt->copy()->endOfDay()` (a full datetime upper bound) instead of `->toDateString()`. This applies to every FIN module with aging buckets, statements, or "as at" reporting (FIN-01, FIN-03's aging, FIN-05's reconciliation as-at dates, etc.) — check for this pattern whenever a new date-cutoff query is added.

## DECIMAL columns need an explicit decimal:N cast or arrive as float
A `$table->decimal('rate', 20, 10)` column with no explicit Eloquent cast is returned as a PHP **float**, not a string, in this app's driver setup — silently defeating bcmath-based `Money` arithmetic, which requires string factors (`Money::multiplyBy(string $factor)` throws a TypeError on a float). Always add `'column' => 'decimal:N'` to the model's `casts()` for any DECIMAL column feeding into `Money`/bcmath — this guarantees a fixed-precision string, not just PHP's default float coercion. Found on `ExchangeRate::rate`/`inverse_rate` (FIN-06); check any future FIN-* decimal column (tax rates, budget variances, depreciation rates, etc.) for the same trap.

## A superseded exchange rate is still correct for its own historical window
`ExchangeRate.status` moves `active` → `superseded` when a newer rate is captured for the same pair, but resolving a rate "as at" a **backdated** date must NOT filter to `status = 'active'` only — a superseded rate is exactly right for dates within its own original `[effective_from, effective_to)` window (that's the whole point of BR-FIN-06-008: a receipt backdated to last week uses last week's rate, not today's). `RateResolvingCurrencyConverter::rateInEffectAt()` filters `whereIn('status', ['active', 'superseded'])` and excludes only `pending`/`rejected` (rates that never took effect). Filtering to `active` alone silently breaks every backdated FX lookup — caught by AC-FIN-06-006's test, not by a type error, so it's easy to ship unnoticed.

## Financial transaction tables use BelongsToSchool + explicit PeriodGuard, never BelongsToSession
Journal already established this (Book B FIN-01): a table recording a financial transaction (learner_fee_assignments, billing_runs, ad_hoc_charges, fee_structures) uses `BelongsToSchool` only and calls `PeriodGuard::assertWritable($model)` explicitly from its own `booted()` — never the `BelongsToSession` trait.

Why: `BelongsToSession`'s global scope does `whereRaw('1=0')` (silently returns nothing) whenever `SessionContext::isSet()` is false — fine for academic/session-scoped tables the current UI session is "looking at", wrong for financial records that must stay queryable by id/report regardless of whatever term happens to be ambient right now. It also auto-fills a null `term_id` from `SessionContext::termId()` on create, which breaks a deliberately-nullable `term_id` (e.g. `fee_structures.term_id` meaning "applies to all terms in the year").

How to apply: for a new Finance model with `academic_year_id`/`term_id`, default to `BelongsToSchool` + a `booted()` `creating`/`updating` hook calling `PeriodGuard::assertWritable($model)` (mirrors [[academic]]'s note on the same BelongsToSchool-only pattern for `learner_subject_enrolments`/`student_enrolments`). Only reach for `BelongsToSession` if the table is genuinely meant to disappear from view outside its owning session — rare outside Core's own session-scoped setup tables.

## FIN-03 owns invoice/journal posting — CommitBillingRunAction delegates to it
`IssueInvoicesForAssignmentAction` (FIN-03) is now the single place that turns a computed `LearnerFeeAssignment` into real financial artifacts: it calls People's `LiabilityResolver` to split the assignment's lines across billed parties, creates one `Invoice` per (guardian, currency) pair, and posts one `FEE_BILLING` journal per invoice (Dr Fee Debtors subledgered to the guardian / Cr Fee Income per component).

`ComputeBillingRunAction`'s own `CommitBillingRunAction` (FIN-02) does NOT post journals itself — it delegates per-assignment to `IssueInvoicesForAssignmentAction`, sharing one `journal_batch_uuid` across the whole run. Do not reintroduce direct `PostJournalAction` calls in `CommitBillingRunAction`; that was the pre-FIN-03 stand-in and posting from both places would double-count revenue.

One invoice per (billed party × currency), never one multi-currency invoice — `invoices.currency` is a single NOT NULL column despite Book B §3's worked example showing a party's USD and ZWG amounts under one invoice number in prose. `billed_party_type` is always `'guardian'` in this pass (a `Guardian` row's own `guardian_type` distinguishes individual vs organisation) — `sponsor`/`employer`/`organisation` as distinct billed-party types is deferred.

## FIN-04 is an intentionally scoped receipting/cashiering engine
Built: `tills`, `till_sessions` (blind cash-up: `DeclareTillCountAction` records the count before `RevealAndCloseTillSessionAction` is ever allowed to compute `expected_closing` — enforced server-side via `TillDeclarationRequiredException`, not a hidden UI route), `receipts`/`receipt_tenders`/`receipt_allocations`/`suspense_items`, `InvoiceAllocationEngine` (oldest-first / component-priority / manual, one currency at a time), `CreateReceiptAction`, `VoidReceiptAction`, `ResolveSuspenseItemAction`, `ClearChequeAction`.

Every receipt's tenders share the receipt's own single `currency` — a receipt mixing tender currencies is deferred. A cheque tender debits cash/bank in full at receipt time but its credit side goes to an explicit `unclearedChequeAccountId`, not a debtor account, until `ClearChequeAction` runs — the learner's balance genuinely doesn't move until then (BR-FIN-04-018/AC-FIN-04-010). `InvoiceAllocationEngine::allocate()` settles a whole invoice by distributing across its lines by *original* `net_minor` share (`Money::allocate()`), not a tracked per-line balance — exact for one-pass settlement, a documented approximation for an invoice paid down across several receipts.

Every "which GL account" decision (cash/bank, suspense, credit-balance, uncleared-cheque, cash-over-short) is an explicit parameter on the relevant Action's DTO — there is no system-account auto-provisioning. `CreateCreditNoteAction` (FIN-03) was retrofitted in this pass to actually decrement a linked invoice's `credited_minor`/`balance_minor` — it previously posted the journal but never touched the invoice's own cache columns.

Deliberately NOT built: reallocation (`ReallocateReceiptAction`), ZWG cash-rounding to the Rounding account (BR-FIN-04-022), SMS/WhatsApp receipt confirmation (needs CORE-09, doesn't exist), actual FDMS fiscalisation (FIN-13, `fiscalisation_status` is set but nothing submits), banking sheets, and the till-open-blocks-period-lock / suspense-blocks-period-lock cross-cutting rules (BR-FIN-04-007/013 — would need changes inside Core's own period-lock action).

## FIN-05 is a driver-abstraction-only gateway/reconciliation engine
Built: `payment_gateways`, `payment_intents`, `gateway_webhooks` (append-only, `UNIQUE(driver, payload_hash)` replay protection — a genuine duplicate delivery is detected and returned as the SAME existing row, never a second row with a mangled hash), `bank_accounts`/`bank_statements`/`bank_statement_lines`, `reconciliation_runs`. `PaymentGatewayDriver` interface matches Book B FIN-05 §4 exactly; `FakePaymentGatewayDriver` is the ONLY registered implementation — ContiPay/Pesepay/Paynow/SmilePay each need real sandbox credentials and a live HTTP integration this build has neither of, so they're not built rather than fabricated against unverifiable behaviour. `PaymentGatewayDriverRegistry` (bound as a singleton in `FinanceServiceProvider::register()`) is where a real driver gets added later — one more `register()` call, nothing else changes shape.

`SettleGatewayPaymentAction` is the single place a confirmed settlement (from `IngestGatewayWebhookAction` OR `PollPendingIntentAction`) becomes a real `Receipt` via FIN-04's `CreateReceiptAction` — idempotent because an already-`succeeded` intent returns untouched, which is the whole mechanism behind "the same settlement delivered five times produces exactly one receipt." Gateway fee accounting required extending `CreateReceiptData` with `gatewayFeeMinor`/`gatewayFeeExpenseAccountId`: the tender amount stays the full gross (so invoice allocation credits the learner the gross), and the fee posts as an extra Dr fee-expense / Cr the-same-settlement-account pair in the SAME journal, netting that account's own movement down to gross-minus-fee without the allocation side ever seeing anything but gross.

`CreateReceiptAction`'s `tillSessionId` is now nullable — a gateway-settled receipt has no till session, and `debitTenderLines()` requires an explicit `bank_account_id` per tender when there's no till to fall back to.

Deliberately NOT built: real disbursement-based refunds (the driver's `disburse()` is declared but never called — `RefundPaymentAction` posts a plain bank debit instead), CSV/OFX statement upload and column mapping (import takes already-parsed line data), fuzzy amount/date-proximity/description bank matching (only exact-reference auto-match on import, `MatchBankStatementLineAction` is the manual-confirm path for anything below that), `RECEIPT_NO_BANK`/`GL_VARIANCE`/`FEE_UNPOSTED` reconciliation exception classes, gateway health-check scheduling, and the reconciliation-blocks-period-close cross-cutting rule (same Core-touching deferral as FIN-04's).
