# People

## PPL-03 is an intentionally minimal Guardian/Liability slice
Built solely to close FIN-03's billed-party dependency (Book B FIN-03 §3/§4 explicitly needs `fee_liabilities` and the liability resolution algorithm). Built: `guardians`, `student_guardian` (the rights matrix — only `is_primary_contact`/`is_emergency_contact`/`is_fee_responsible`/`may_collect_learner`/`may_view_full_balance`/`has_court_restriction` kept), `fee_liabilities`, `LiabilityResolver` (percentage rules round independently against a shared base — never batched through `Money::allocate()`, so a genuinely partial percentage split correctly falls through to the residual guardian per BR-FIN-03-007), `CreateGuardianAction`/`LinkGuardianToStudentAction`/`DeactivateStudentGuardianAction`/`CreateFeeLiabilityAction`.

Deliberately NOT built: `households` (sibling discounts/combined statements), `sponsorships` (budget envelopes, performance conditions), `guardian_verification` (gate terminal ID checks), portal provisioning, duplicate detection, the contact-update approval queue, and the liability-designer screen's "shares must total 100%" live check (the resolver itself tolerates and correctly resolves an incomplete split instead).

`CreateStudentAction` (PPL-01) still does not create or require a guardian — a student with zero guardians is possible in this codebase and will throw `NoFeeResponsibleGuardianException` the first time anything tries to invoice them. Every test/fixture that calls `IssueInvoicesForAssignmentAction` (directly, or via `CommitBillingRunAction`) must link at least one `is_fee_responsible` guardian first.

## PPL-01's admin UI pass found four tables in its own spec that were never built
Four of `students`' own sibling tables — `student_documents`, `student_prior_schools`, `student_siblings`, `student_timeline` — have no migration, model, or Action at all (verified directly: `Modules/People/database/migrations/` has no file for any of them). This was never flagged anywhere before this pass. Building `People\Students\Documents`/`PriorHistory`/`Siblings`/a real `Timeline` tab needs the backend built first — that is new backend work, not an admin-UI retrofit, and is deliberately **not** done here. `People\Students\Show`'s own tabs (Overview/Academic/Financial/Guardians) are what's real today; "Academic" folds billing-attribute history in as the closest stand-in for a timeline.

Also not built, confirmed by the same check: `AllocateToClassAction`/`AllocateToHouseAction` (the balancing algorithms `People\Allocation\Classes`/`Houses` would need), `BulkAllocateClassesAction` (draft→review→commit), `GenerateIdCardAction`, and `MergeDuplicateStudentsAction` (`DetectPossibleDuplicatesAction` only ever flags, via a stateless check with no persisted queue — see its own docblock). None of these five screens exist in this pass either.

`PreviewBillingAttributeChangeAction` (new, for `People\Students\ChangeAttribute`'s live fee-impact preview) reuses `FeeStructureResolver`/`FeeLineCalculator` against an **unsaved clone** (`$student->replicate()`) of the real learner with the proposed attribute applied — both classes read straight off whatever `Student` instance they're given (including its lazy relations, re-resolved correctly once a FK like `grade_level_id` changes on the clone), so this works without persisting anything or touching `ChangeBillingAttributeAction`'s own history write.

## `DetectPossibleDuplicatesAction`'s name+DOB match was silently broken
`date_of_birth` is declared `$table->date(...)`, but the stored value round-trips as a full datetime string ("2015-03-10 00:00:00", confirmed via `getRawOriginal()`) — the same class of trap `.ai/rules/finance.md` already documents for `effective_at`. The original code compared it with a plain `where('date_of_birth', $date->toDateString())` (bare "Y-m-d"), which **never matched**, silently, for every school since this action was built — caught only by this pass's own admin-UI test, not by any prior test. Fixed to `whereDate(...)`, which compares the calendar date portably regardless of how the driver stores it. Check any future exact-date comparison against a `date()`-cast column the same way.

## PPL-03's admin UI pass: the Liability designer was already built, under Finance
`Finance\Liabilities\Editor` (`Modules/Finance/Livewire/Liabilities/Editor.php`, route `finance.liabilities.editor`) already is PPL-03's own "Liability designer" screen — it shipped during the FIN-03 admin-UI pass, calling `CreateFeeLiabilityAction`/`DeactivateFeeLiabilityAction` directly (see that screen's own docblock). Don't build a second one under `Modules/People/Livewire/` — link out to the Finance route instead, exactly as `People\Guardians\Show` does.

What this pass *did* build, all genuinely backed: `People\Guardians\Index`/`Show`/`Create` (create-only — no `UpdateGuardianAction` exists, matching the same create-only precedent as other screens this pass), and `People\Students\Guardians` (the student-scoped relationship editor backed by `LinkGuardianToStudentAction`/`DeactivateStudentGuardianAction`, replacing the "Guardians" tab's old "not yet built" placeholder on `People\Students\Show`).

Still deliberately not built, same reasons as before: Households, Sponsorships, Portal access, Contact update queue, Duplicate review, Verification — none of their tables exist.

## PPL-02's admin UI pass: what has a real backend and what doesn't
The domain layer covers the whole paid pipeline — `CreateIntakeAction`, `SubmitApplicationAction`, `PayApplicationFeeAction`, `OfferApplicationAction`, `AcceptOfferAction`, `PayAcceptanceDepositAction`, `DeclineApplicationAction`, `ExpireOfferAction`, `ConvertApplicationToStudentAction` — so this pass built real screens for all of it: `Admissions\Intakes\Index` (list+create), `Admissions\Applications\Index` (also stands in for the spec's separate "Waiting list" screen — same table, filtered to `status = waitlisted`, so no second screen was built), `Admissions\Applications\Create` (the staff-facing stand-in for the spec's unauthenticated public form, which has no controller built in any pass — BR-PPL-02-001's own public endpoint is still entirely unbuilt), `Admissions\Applications\Show` (one lifecycle screen hosting the whole action bar — pay fee, offer, decline, accept, pay deposit, expire offer — rather than a screen per spec-named transition, mirroring `Finance\Till\CashUp`'s own shape), and `Admissions\Applications\Convert` (preflight + a guardian-match preview that re-runs the Action's own phone-match query read-only, deliberately not a second Action).

Each mutating method on `Show` checks its own finer permission inline (`people.admissions.offer_make` / `.application_review`) rather than at `mount()`, per `AuthorizesPermissions`'s own documented standard — `mount()` only requires the baseline `.application_view`.

Genuinely absent from the backend (verified: no migration, no model, no Action) — **Enquiries** (`enquiries`/`enquiry_activities`, the CRM kanban pipeline), **Entrance exams** (`entrance_exams`/`entrance_exam_candidates`, scheduling/seating/marking), **Interviews** (`interviews`, panel scorecards), and **Funnel analytics** (no aggregation action exists, and a real funnel needs the enquiries data that doesn't exist either). None of `Admissions\Enquiries\Board`, `Admissions\Exams\Manage`, `Admissions\Interviews\Schedule`, or `Admissions\Reports\Funnel` were built. This is new backend work, not a UI retrofit.

`Account::where('is_postable', true)` (no system-key filtering) is used for every bank/income/refundable-deposits account picker in `Show`/`Convert` — the exact pattern `Finance\Receipts\Capture` already uses for the same reason: there's no seeded system key for "income" or "refundable deposits" specifically (only `credit_balance`/`suspense`/`uncleared_cheque`/etc. are), so the bursar picks the right one from the full postable chart rather than the screen guessing.

## Livewire cannot hold an arbitrary DTO object (or an array of them) as a public property
`BillingAttributeChangePreview`/`DuplicateCandidate` objects, assigned directly to a public Livewire property, either throw ("Property type not supported in Livewire for property") or — worse — silently come back empty after the next server round-trip, with no error at all (an array of `DuplicateCandidate` objects did this: the action found the match, but `$component->get('duplicates')` read back `[]` after the next `->call()`). Convert any DTO/DTO-array to a plain array (or scalars) the moment it's assigned to a public property; only read the rich object inside the same method call that produced it.

## PPL-04's admin UI pass: a large, well-covered module — one genuine gap, three deliberate simplifications
The backend covers nearly the whole spec (27 Actions across Staff/Contracts/Establishment/Allocation/Workload/Leave/Duty/Appraisal/Disciplinary/Exit/Documents). Built: `People\Staff\{Index,Show,Create,Contracts,Disciplinary,Compliance}`, `ExitProcessing` (not `Exit` — see below), `People\Establishment\Index`, `People\Allocation\TeacherMatrix`, `People\Leave\{Request,Approvals,Balances}`, `People\Duty\Rosters`, `People\Appraisal\{Index,Show}`.

**Genuine backend gap**: `staff_qualifications` (degrees/certificates/teaching subjects covered) has no migration, model, or Action at all — no Qualifications tab/screen exists on `Staff\Show`. `AllocateTeacherAction`'s own docblock already names this as why BR-PPL-04-005's qualification check is skipped (warning, not block).

**Deliberate simplifications, each documented in its own screen's docblock**: (1) this whole admin panel is internal-staff-facing throughout (CLAUDE.md's own tech-stack table), not an employee self-service portal, so the spec's "own"-scope screens (Leave Request, My Duties) became HR-facing capture-on-behalf-of screens instead, and the separate "Leave calendar"/"My duties" screens were folded into Balances/Approvals and Rosters respectively rather than built as near-duplicates; (2) `Allocation\TeacherMatrix` is a pick-and-submit form, not the spec's "drag teachers into a grid" interaction — a UX nicety the backend doesn't require; (3) `Appraisal\Show`'s self/appraiser assessment content is one free-text note under a `notes` key, not a structured rubric — no criteria list exists anywhere in this backend to render a structured form against.

**A class literally cannot be named `Exit`** — `exit` is a reserved PHP language construct; `php -l` throws a parse error on `final class Exit`. The screen is `People\Staff\ExitProcessing` instead; the route name (`people.staff.exit`) is unaffected.

**New, small, honest additions, not business logic**: a `staff_document` `FileCategoryRegistry` entry (`PeopleServiceProvider::registerFileCategories()`) so `Staff\Compliance`'s upload form has a real file category to upload into — `AddStaffDocumentAction` needs a genuine `files.id`, and none of CORE-10's existing categories fit. `CheckStaffDocumentExpiryAction` takes positional `(int $schoolId, ?Carbon $asOf)` args, not a DataObject — don't wrap it in one that doesn't exist.

**Disciplinary confidentiality (BR-PPL-04-020) is enforced by never querying the sensitive columns in a list.** `Staff\Disciplinary`'s case list selects only `id`/`case_number`/`category`/`stage`/`incident_date`/`is_confidential` directly — `description`/`outcome` are never in that query. Opening a case's full detail calls `ViewDisciplinaryCaseAction` (the only sanctioned read path, per that Action's own docblock) and immediately flattens the result to a plain array property, per this file's own DTO-on-a-public-property rule above.
