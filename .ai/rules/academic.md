# Academic

## Academic module is an intentionally minimal ACA-01/ACA-02 slice
Built solely to close the ACA-02 subject-count dependency FIN-02 (Book B) was specified against (BR-FIN-02-004) — not the full Book D spec. Built: curriculum_frameworks, subject_groups, subjects, subject_selection_rules (block/warn rule engine covering min_total/max_total/min_from_group/max_from_group/required_subject/mutually_exclusive only), learner_subject_enrolments (⭐ the billing source of truth), subject_enrolment_changes (append-only proration snapshot), SubjectEnrolmentQuery (the FIN-02 contract), EnrolSubjectAction/DropSubjectAction.

Deliberately NOT built yet (at the time this module's backend was first laid down): `pathways` table (Student.pathway stayed a plain string), `level_subject_offerings`, `subject_prerequisites`, `syllabi`, `class_allocations`, `teaching_groups`, `subject_selection_submissions`. All of these joined the module in later backend passes — see the `Book D admin-UI pass` sections below for what the UI retrofit found once every ACA-01/02/04/05 table existed.

## subject_selection_rules keeps its plain-string pathway column, not pathway_id FK
Book D ACA-01's spec defines `subject_selection_rules.pathway_id` as a FK to the new `pathways` table. When `pathways` was built (completing ACA-01), this column was deliberately LEFT as its already-shipped plain string `pathway` rather than migrated to `pathway_id` — refactoring it would have touched `SubjectSelectionRuleEngine`, `EnrolSubjectAction`, and the already-passing ACA-02 billing tests for a completeness detail with no functional gap (string matching works identically to FK matching here since `Student.pathway` is also a plain string, not itself an FK).

New ACA-01 tables that don't have this legacy constraint (`level_subject_offerings`) use the proper `pathway_id` FK from the start. If a future pass needs `subject_selection_rules` to join against the `pathways` catalog (e.g. for the rule-builder screen to show pathway names, not codes), that's the point to do this migration — not before.

## Academic never depends on Finance directly — cross-module fee data flows through the caller, not a new Action-to-Action call
Every existing cross-module reference between these two modules runs Finance → Academic (Finance imports Academic's models/events: `BillMidTermSubjectChangeAction`, `RaiseMidTermSubjectChangeBillingListener`, `FeeStructureResolver`'s `SubjectEnrolmentQuery` dependency). Academic has never imported anything from `Modules\Finance`, and that should stay true.

When an Academic workflow needs a Finance-computed figure (e.g. `SubjectSelectionSubmission.indicative_fee_minor`, per Book D ACA-02 §7/BR-ACA-02-016), don't have the Academic Action call into Finance to compute it. Instead: Finance exposes its own standalone Action (`Modules\Finance\Domain\Actions\PreviewIndicativeFeeAction`), the caller (a controller, or whatever layer sits above both modules) calls that action first and passes the resulting figure into the Academic action's Data object as a plain nullable field. `SubmitSubjectSelectionAction` just stores what it's given — it never resolves the fee itself.

**Why:** avoids a first-ever Academic→Finance dependency, keeping the module graph acyclic exactly as it's been throughout the codebase. See `SubmitSubjectSelectionAction`'s docblock for where this was decided. Related: [[Collection<K,V> is invariant in PHPStan/Larastan — use plain array<int,V> for override params passed across method boundaries]].

**Admin-UI pass note:** this still holds even though `Modules\Academic\Livewire\Enrolment\LearnerSubjects` and `Selection\Form` now call `Modules\Finance\Domain\Actions\PreviewIndicativeFeeAction` directly — that call happens from the Livewire layer (the "caller" this rule means), not from an Academic domain Action. `Modules\Academic\Domain\Actions\**` still imports nothing from `Modules\Finance`.

## Book D admin-UI pass: ACA-01's own catalogue had zero domain Actions before this pass
`CurriculumFramework`, `Subject`, `SubjectGroup`, and `SubjectSelectionRule` each had a model, migration, and factory, but **no Action anywhere ever created one** — verified directly (`grep -rn "CurriculumFramework::create\|SubjectGroup::create\|Subject::create\|SubjectSelectionRule::create" Modules/Academic` returns nothing outside factories/tests; every pre-existing row came from `::factory()->create()` in a test or `AcademicServiceProvider::registerTenantModels()`'s demo data). This pass added four small, create-only Actions to close that gap: `CreateCurriculumFrameworkAction`, `CreateSubjectGroupAction`, `CreateSubjectAction`, `CreateSubjectSelectionRuleAction` — each a plain `Model::create()` wrapped in `$this->transaction()`, no business logic beyond what the model's own migration already enforces. None has an `Update` counterpart, matching this project's established create-only precedent elsewhere (Staff, Guardians, Intakes).

## `CurriculumFrameworkFactory`'s default code is `'HBC_2024'`

## `Marks\Amend` now genuinely routes a published mark's amendment through CORE-07 (built 2026-10-07)
`AmendMarkAction` used to accept a caller-asserted `approved: true` flag and `Marks\Amend` passed it unconditionally — a published amendment always went straight through, gated only by holding `academic.result.amend_published`, with no real approval behind it despite the docblock's claim otherwise (a stale-doc/code mismatch this session also fixed). Replaced with the real thing, mirroring `DiscountAward`'s own `Approvable` wiring (Book K FIN-07):
- `AmendMarkAction` now refuses a `published` assessment unconditionally (`MarkAmendmentRequiresApprovalException`) — there is no bypass flag left to pass.
- `ApplyMarkAmendmentAction` holds the actual write (version row + mark update + class/level cascade + report regeneration) that `AmendMarkAction` used to do inline. It trusts its caller completely and has no gate of its own — by design, the same way `DiscountAward::onApproved()` trusts the approval engine rather than re-checking anything.
- `RequestMarkAmendmentAction` is the only way to amend a `published` mark: creates a `MarkAmendmentRequest` (new `Approvable` model, `approvable_type` = `mark_amendment`) and routes it through `RequestApprovalAction`. `MarkAmendmentRequest::onApproved()` is the only other caller of `ApplyMarkAmendmentAction`.
- A school must configure an active approval chain for the `mark_amendment` type via the existing `Approvals\ChainBuilder` screen before this works — `RequestApprovalAction` throws `NO_APPROVAL_CHAIN` otherwise, same as any other first use of a new approvable type (no seeding, no special-case wiring needed anywhere else).
- `Marks\Amend` branches on `$assessment->status`: not-published amends immediately via `AmendMarkAction`; published calls `RequestMarkAmendmentAction` and shows a pending-requests table with a link to `Approvals\Show` for tracking. Tests: `MarkAmendmentApprovalTest.php` (6 tests), plus the two pre-existing ACA-05 tests that used to assert `approved: true` directly now exercise the full request → `ApproveStepAction` round-trip.

## Permissions are registered under module code `ACADEMIC`, so every check string carries the `academic.` prefix automatically
`AcademicServiceProvider::registerPermissions()` registers bare `resource.action` paths (e.g. `curriculum.manage`) via `PermissionRegistry::register('ACADEMIC', [...])` — the synced permission name is `academic.curriculum.manage`, not `curriculum.manage`. Every `authorizePermission(...)` call in `Modules/Academic/Livewire/**` already carries the full `academic.` prefix; a new screen's permission string must too, or `PermissionScopeResolver::has()` will look up a name that was never registered and refuse every user, including a super-admin test fixture.

## Book E admin-UI pass: a public `$slots` property on a Livewire component silently breaks every render
`Timetable\Structures` originally declared `public array $slots = [];` for its period-slot repeater rows. Livewire's own `Component::getSlots()`/`SupportSlots` hook reads a property it expects to hold `Slot` objects under that exact name — a plain array there makes `SupportSlots::dehydrateSlotsThatWerePassedToTheComponentForSubsequentRenders()` fatal with "Call to a member function getName() on array" on *every* render, including the very first GET request. No validation error, no 403, no helpful message — just a 500 with a stack trace deep in Livewire internals that names neither your component nor your property. Confirmed by renaming the property to `slotRows` and nothing else. **Any new Livewire component must avoid `$slot`/`$slots` as a public property name**, full stop — grep a new component for this before writing its first test if its render fails with that exact "getName() on array" signature.

## Book E admin-UI pass: `Auth::id()` is a `users.id` — several ACA-06/07 Actions take a `staff.id` instead, and the two are never interchangeable
Unlike every Book D screen this pass copied its shape from (`Marks\Entry`'s `enteredByUserId`, `Marks\Amend`'s `changedByUserId` — both genuinely `users.id`), a cluster of Book E Actions take the *acting staff member's* id: `ApproveProjectBriefData::$approvedByStaffId`, `MarkProjectData::$markerStaffId`, `ModerateProjectData::$moderatorStaffId`, `VetExaminationPaperData::$vettedByStaffId`, `EnterExamMarkData::$markerStaffId`, `EnterThirdExamMarkData::$markerStaffId`, `ModerateExamMarkData::$moderatorStaffId`. This pass's first draft of `Projects\Approve`/`Mark`/`Moderate` and `Exams\PaperVault`/`MarkEntry`/`Variance`/`Moderate` all passed `(int) Auth::id()` straight into these — compiling fine, passing PHPStan fine (both are plain `int`), and silently writing the wrong row's id as the marker/vetter/approver every time, since a `users.id` and a `staff.id` are different sequences that only coincidentally share small integers in a fresh test database. Caught only by writing an admin-UI test that actually exercises the full lifecycle (approve → issue; vet → seal → release) and watching a status refuse to advance. Fixed by resolving `Staff::where('school_id', $this->school->id)->where('user_id', Auth::id())->value('id')` in each affected method, toasting "no staff record linked" and returning early when it comes back null rather than ever falling back to the wrong id. The same bug hid a second time in `Exams\Scripts`: `HandoverScriptBatchData`/`CollectScriptBatchData` take *both* a `staff.id` (`toStaffId`/`collectedByStaffId`, correctly chosen from a dropdown) *and* a separate `recordedByUserId` (a real `users.id`) — the first draft passed the staff id for both. No codebase-wide helper resolves "the current user's staff record" as of this pass (grepped for `currentStaff`/`actingStaff`/similar — nothing); a future screen needing it will have to inline the same `Staff::where('user_id', ...)` lookup shown above until one exists.

## Book E admin-UI pass: `LessonSubstitutionFactory` had the same lazy-factory double-resolution bug `TimetableSlotFactory`'s own docblock already diagnosed and fixed
`TimetableSlotFactory`'s docblock explains the trap: a lazy `Factory` instance (`$term = Term::factory()->...`) referenced as a plain attribute value in two places in one `definition()` is resolved *independently* each time, not deduped — each reference creates its own row, tripping the `(school_id, academic_year_id, number)` unique constraint on `terms` the moment both resolve under the same school. `LessonSubstitutionFactory` had the identical shape (`$term` used directly for `term_id` *and* nested inside `TimetableSlot::factory()->state(['term_id' => $term])`) and had simply never been exercised by a bare `::factory()->create()` call before this pass's own `Timetable\Cover` test wrote one. Fixed the same way `TimetableSlotFactory` already was: create `$school`/`$year`/`$term` eagerly with `->create()` before building the returned array, so every reference resolves to the same already-persisted row. If a future factory in this module chains more than one reference to the same lazy relationship, create it eagerly first — don't assume Eloquent factories deduplicate a repeated lazy value.

A real bug caught by this pass's own tests: `learner_projects.outcome` is never written anywhere in the domain layer — `EloquentContinuousAssessmentProvider::outcomeFor()` derives "outcome" from the `status` column instead — so both new Actions check `status === 'verified'`, not the always-null `outcome` column a first draft wrongly checked. `ProjectNationalSubmission` is the audit-trail row, same shape as `ProjectPortfolio`/`BoardPack`. An admin screen for learner-facing milestone/evidence submission remains deliberately deferred too — the spec places that on the mobile app/portal, not the staff console.

**ACA-07** (14 screens): `Exams\{Sessions,Papers,PaperVault,Candidates,Seating,Invigilation,Scripts,MarkEntry,Variance,Moderate,Arrangements,Malpractice,Results,Analysis}`. `Sessions` folds in a new gap-filling `AdvanceExaminationSessionStatusAction` (nothing else ever advanced a session past `planning`). `Seating` also serves as the spec's separate "Attendance sheets" screen. `Malpractice` is gated behind its own dedicated `malpractice_view`/`malpractice_manage` permissions, never the general `exams.manage`, so this screen is the Livewire-layer confidentiality enforcement `ReportMalpracticeIncidentAction`'s own docblock names as pending. **Correction (2026-10-08)**: `CMP-01`'s candidate-set export and `FIN-02` entry-fee billing were listed here as deferred gaps, but both were already closed by Book H3's `CMP-01` work (`DeriveZimsecCandidatesAction` consumes the `ExaminationCandidateSet` interface this book opens; `BillZimsecEntryFeesAction` raises the `FIN-02` ad hoc charge) — stale notes, not real gaps, the same situation as the FIN-12 Board-pack/PriorPeriod corrections. **Gap closed**: `Analysis` (`AnalyseExaminationSessionAction`) computes grade distribution, subject comparison, and a year-on-year trend from marks `ProcessExaminationResultsAction` already settles — session-scoped and deliberately not a duplicate of `ACA-05`'s own term-level subject aggregation. Reuses the existing `exams.view` permission rather than minting a near-duplicate `results_view`. **Gap closed (2026-10-08): encryption at rest.** `UploadExaminationPaperFileAction`/`DownloadExaminationPaperFileAction` mirror `CreateBackupAction`'s own `Crypt::encryptString()`/`decryptString()` cycle rather than the generic `UploadFileAction` (which writes plaintext and queues jobs that make no sense against ciphertext). A file can only be attached/replaced while `draft`/`vetted`; sealing locks it, matching `SealExaminationPaperAction`'s own doctrine. Every download re-runs the real release gate first. **Gap closed (2026-10-08): visible watermarking.** `DownloadExaminationPaperFileAction` stamps every served PDF via a new `Modules\Academic\Domain\Support\PdfWatermarker` (`setasign/fpdi` + `setasign/fpdf`) naming the downloading user and the download timestamp — applied to the decrypted bytes on every call, never baked into the stored ciphertext. `intervention/image` (the user's first pick) turned out unable to open a PDF at all without `imagick`/Ghostscript, neither reliably available in this environment — surfaced before writing code; user said "do what's best", hence FPDI/FPDF (pure PHP, imports pages rather than rasterising). A stored file that isn't a parseable PDF is served unstamped (`FpdiException` caught) rather than failing a gated, logged download. Nothing from ACA-07's original scope remains deferred.

## LMS screens: teacher-scoped via AuthorizesCourseSpace; content and chase validated server-side
Academic/Livewire/Lms/* (routes academic.lms.*, perms lms.*). Every component re-authorises the course space through AuthorizesCourseSpace: school-reach holders manage any space, others only spaces whose teacher_staff_id is their own Staff row. ContentItem links must be http(s) (rendered as anchors), file size comes from the stored File, an unscanned/infected file cannot be published. ChaseNonSubmittersAction re-derives genuine non-submitters (the id list is tamperable). PostDiscussionMessageAction checks authorship against the space (staff = its teacher, student = active member). Blade: use $collection->get($id)?->x, not $collection[$id]?->x — a missing key raises 'Undefined array key'. AssignmentSubmission::factory() makes its OWN assignment and a student in another school unless student_id/assignment_id are passed.

## CBT: time is the server's; marking queue limited to written items of the chosen test
Academic/Livewire/Cbt/* (routes academic.cbt.*, perms cbt.*). The candidate test-taking screen is the learner app's job — nothing in the staff panel answers for a candidate. SaveResponseAction refuses once CbtCandidateAttempt::remainingSeconds() is 0 and refuses a question not on the test; SubmitAttemptAction marks any expired submission auto_submitted; CloseCbtTestAction submits in-flight attempts; AutoSubmitExpiredAttemptsAction sweeps expired ones. RecordFocusEventAction only logs while an attempt is live and focus monitoring is on; flags above max_tab_switches (fallback cbt.default_max_tab_switches) — never penalises. Question type decides auto-markability (essay/file_upload never auto; mcq/true_false/matching always). A test's status 'flagged' is attempt-level and is lost on submission — the monitor derives the review flag from tab_switch_count > limit. Tests: write a response BEFORE rewinding started_at.
