# Domain Actions

## Revoke Sanctum tokens via revoked_at, never $user->tokens()->delete()
This codebase's own token model (`Modules\Core\Models\PersonalAccessToken`, bound via `Sanctum::usePersonalAccessTokenModel()`) revokes a token by setting `revoked_at`/`revoked_by` (see `RevokeTokenAction`), never by deleting the row — `isRevoked()` checks that column, and `RefreshToken` rows linked to the access token are marked `used_at` at the same time. Hard-deleting via `$user->tokens()->delete()` bypasses all of that (no audit trail, linked refresh tokens left dangling, no `TokenRevoked` event).

Rule: whenever an Action needs to revoke a user's tokens (staff exit, account suspension, etc.), reuse the existing `RevokeTokenAction` per token (looping over `$user->tokens()->whereNull('revoked_at')->pluck('id')`) rather than reimplementing revocation or deleting rows directly.

## A 'date'-cast column is stored with a "00:00:00" time suffix — use whereDate(), never ->where(col, $dateString), for exact-date equality
Eloquent's `'date'` cast (e.g. `attendance_sessions.session_date`) persists to the DB as `'Y-m-d 00:00:00'`, not a bare `'Y-m-d'` — confirmed via `DB::table(...)->pluck(...)` on SQLite (the test driver). A query like `->where('session_date', $carbon->toDateString())` (bare `'Y-m-d'`) silently matches zero rows, since it's comparing against the full datetime string.

Inequality comparisons (`<=`, `>=`, `>`) against a bare `'Y-m-d'` string still work by accident (string comparison treats the shorter prefix as less-than), which is why this bug hides in code that only ever does range checks (`effective_from <= X`) and only surfaces the first time something does an exact-date match.

**Fix:** always use `->whereDate('column', $dateString)` for exact-date equality against a date-cast column — never bare `->where()`. Found and fixed in `RecordMarkingComplianceAction` (Book D ACA-04) while debugging why it always computed zero expected sessions.

## Book A CORE-09's notification bus is real and now has its first production caller (ACA-04) — reuse this pattern, don't rebuild a channel/dedupe mechanism
`Modules\Core\Domain\Actions\Notifications\DispatchNotificationAction` (+ `NotificationKeyRegistry`, `NotificationTemplate`, `NotificationChannelDriverRegistry`) was fully built but had ZERO non-test callers anywhere in the codebase until `Modules\Academic\Domain\Actions\MarkAttendanceAction` (Book D ACA-04 §7/BR-ACA-04-006) wired it for the unexplained-absence alert. Before building any new "notify someone" feature (boarding roll call, disciplinary escalation, fee reminders, etc.), use this bus — do not hand-roll a second notification path. Per CLAUDE.md's own "don't rebuild the notification bus" warning for Books I/J.

Wiring checklist, from the ACA-04 example:
1. Register a `NotificationKeyDefinition` in the owning module's `*ServiceProvider::boot()` (e.g. `AcademicServiceProvider::registerNotificationKeys()`) — every provider re-registers on every boot, self-healing against `NotificationKeyRegistry::clear()` calls other test files make.
2. Seed a default (`school_id` null) `NotificationTemplate` per channel via a migration that calls `app(CreateNotificationTemplateAction::class)->execute(...)` directly — safe because provider `boot()` (which registers the key) always runs before any migration.
3. Call `DispatchNotificationAction` AFTER your own write transaction commits, wrapped in try/catch that swallows the exception — messaging must never block/roll back the operation it attaches to.
4. For "one message per person per day" dedup, don't invent a new mechanism: pass a STABLE `relatedType`/`relatedId` pair (e.g. `relatedType: 'attendance_daily_absence', relatedId: $studentId` — not the per-event record id) plus `dedupeWindowMinutes: 1440`. The bus's own dedupe key is `recipientId:notificationKey:relatedType:relatedId`, hashed and checked against `created_at` within the window.
5. `DispatchNotificationAction` always writes a second `in_app` mirror row on a non-suppressed send — a test asserting notification COUNT must filter `where('status', 'sent')` (or `channel != 'in_app'`), never just count all matching rows, or it'll double/triple count.

## Larastan sometimes infers Model::find($id) as never-null — verify with an explicit if-null guard, don't blindly delete the ?-> it flags as redundant
PHPStan/Larastan repeatedly flags `?->` after `SomeModel::find($id)` as `nullsafe.neverNull` ("unnecessary, use -> instead") even though `find()` on a single scalar id is genuinely `?Model` at runtime (the row can not exist). Hit this three times this session: `Student::find()` in `MarkAttendanceAction`, `GradingScale::find()` in `RecomputeSubjectPositionsAction`, and an `AttendanceSession`/`AllocateClassAction::created_at` variant.

**Do not** just delete the `?->` because PHPStan says so — that turns a real runtime null into a fatal error the moment the row is legitimately missing. Instead: assign to a local variable, guard it with an explicit `if ($x === null) { ... }` (return early, or build a nested guarded block), and reference the *local variable* afterward rather than re-deriving the nullable expression inline. This satisfies PHPStan (it can path-narrow a local variable across an explicit `if`) without weakening the actual null-safety. See `RecomputeSubjectPositionsAction::execute()` (Book D ACA-05) for the pattern: `$scale = null; if ($subject !== null && $subject->grading_scale_id !== null) { $scale = GradingScale::find(...); } $lowerIsBetter = $scale !== null && $scale->lower_is_better;` — three lines longer than the nullsafe-chain version, but PHPStan-clean and still actually safe.

## Never do exact/range WHERE comparisons against a 'date'-cast column with a bare date string
Eloquent's `date` cast only affects the PHP-side read value (truncates to midnight when accessed) — on WRITE, the value is still serialized through the connection's full datetime format, so a `'date'`-cast column's stored value is always `"Y-m-d 00:00:00"` (or worse, `"Y-m-d H:i:s"` with the actual time-of-day if you assign a Carbon instance that still carries a time component instead of calling `->toDateString()` first). Two consequences: (1) ALWAYS call `->toDateString()` explicitly before assigning a Carbon/CarbonInterface value to a `date`-cast attribute — never pass the Carbon object directly, or the current time-of-day gets baked into the stored value. (2) Even after that fix, never compare a `date`-cast column against a bare `'Y-m-d'` string with `where($col, $value)` or `where($col, '<=', $value)`/`'>='` — the stored value has a `" 00:00:00"` suffix the bare string doesn't, so exact equality always fails and `<=`/`>=` can silently invert depending on which side has the padding (a stored value equal to the query date compares as *greater than* the bare string, so `col <= bareDate` fails even when they represent the same calendar day). Always use `whereDate($col, $value)` / `whereDate($col, $operator, $value)` (and `orWhereDate`) instead of `where`/`orWhere` whenever comparing a date-cast column against a date computed via `->toDateString()`. Found via `Modules/Boarding`'s BRD-02 roll-call/occupancy queries and BRD-01's bed-allocation date-range queries — both initially used plain `where()` against `roll_date`/`effective_from`/`effective_to` and silently returned wrong result sets.

## Cross-school system Actions must query BelongsToSchool models via withoutGlobalScopes(), not ambient SchoolContext
`SchoolScope` returns zero rows (`1=0`) whenever no ambient `SchoolContext` is set — fine for a normal request-scoped Action, but silently breaks any Action that operates across schools with no single school's context active (e.g. Book J SAA-01's subscription→school_modules sync, which iterates a tenant's `covered_school_ids`). `SchoolModule::updateOrCreate()` under `1=0` never finds an existing row, so a second toggle for the same (school_id, module_code) throws a unique-constraint violation; a plain read silently returns `[]`.

Fix: query explicitly by the known target `school_id` using `Model::withoutGlobalScopes()->where('school_id', $id)...` instead of relying on ambient context — never call `SchoolContext::set()` from inside an Action (Book A Part 1.5 rule). This is the same fix `SwitchActiveSchoolAction` already applies for `AcademicYear`/`Term`, and `ToggleSchoolModuleAction` (Book A CORE-02) now applies internally too — safe for its normal in-context caller since the explicit `where('school_id', ...)` clause makes the global scope redundant there anyway.
