# V1

## /api/v1 controller conventions
Routes live in routes/api.php (prefix api/v1, middleware group serp.api, abilities via serp.token-ability). Return Modules\Core\Http\Support\ApiResponse (success/data/meta; errors use the same envelope with a code). Money is always Money::jsonSerialize(), never a bare number. Parent endpoints resolve "whose child" only through People LinkedLearners (never a client id alone), answer 404 for anyone else's learner, and omit link-gated fields (e.g. balances without may_view_full_balance) rather than hiding them. Financial mutations must sit behind serp.idempotent. Revoked Sanctum tokens are rejected by CoreServiceProvider's authenticateAccessTokensUsing callback.

## `Api/V1/Public/*` — genuinely unauthenticated endpoints, a different convention
A controller under an `Api/V1/Public/` subdirectory (first used by `Modules\People\Http\Controllers\Api\V1\Public\PublicApplicationsController`, Book C PPL-02 BR-PPL-02-001) is NOT routed through the `serp.api` group at all — no `auth:sanctum`, no `serp.token-ability`. It still returns `ApiResponse` envelopes and still lives under `routes/api.php`'s `api/v1` prefix, but its own route group only ever adds `throttle:N,1`. Three things every such controller must do, since nothing else enforces them: (1) resolve its own tenant/school from a public, non-guessable identifier the request supplies (a model's own `ulid`, or a dedicated public slug like `intakes.public_form_slug`) — never infer it from anything else the caller sends, and `SchoolContext::set(...)`/`::clear()` it manually around the Action call since no middleware does this for an unauthenticated route; (2) this project has no real CAPTCHA dependency approved — reuse the honeypot-field-plus-minimum-fill-time pattern `PublicEnquiryController` (the web `/apply/{slug}` equivalent) already established, not a new mechanism; (3) a second write-path action that needs to prove "you are who you say you are" without an account (e.g. uploading a document against an existing public record) should reuse whatever single fact the record's own tracking mechanism already relies on (e.g. BR-PPL-02-015's own `date_of_birth` check) rather than inventing a parallel signed-URL scheme — there isn't one anywhere else in this codebase's public routes to be consistent with.
